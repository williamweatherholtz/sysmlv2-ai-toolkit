# Obligation Review Deck

The human's queue is computed by `keel`; the deck turns it into a page they can operate on a phone.
The page is generated by the ENGINE (`keel deck`, `keel-cli/src/deck.rs`), served by `keel serve` at
`/deck`, and its whole save loop is machine-tested before any deploy
(`.engine/tools/test_deck_e2e.py`, httpx against a served COPY). It is a **`#View`** — regenerable,
never truth. Nothing the human taps is a recorded fact until it lands through the write API and reads
back from a computed view.

## The three transports, and what each one's save label may claim

The page detects its transport at load and says which one it got. **The label ladder is D0018
applied to a button: a claim is verified at the surface that CONSUMES it**, and every rung names its
own rung, never the one above.

| transport | how it saves | what a tap may claim |
|---|---|---|
| **local** (same-origin `/api/version` answers) | `keel serve`'s own POST endpoints | `saved to keel` — earned by the API's 200 plus the e2e-verified computed-view read-back |
| **inbox** (no server; viewer has the Smartsheet connector) | one ROW per tap to the `keel-deck-inbox` sheet via the artifact `mcp` capability | `delivered to inbox row N` — earned by the STORE'S ack (the row id in the reply); keel has it only after the pull below |
| **none** | nothing | `NOT delivered - tell Claude this verdict` |

The live-doc mechanism is retired (issue194): its appends silently dropped — `sync()` resolved,
neither keel nor the viewer's own reload ever saw the write. A transport with no receiver-side
acknowledgment cannot carry a save label. `deck::tests::the_dead_live_doc_mechanism_stays_dead`
keeps it out.

## Procedure

### 1. Serve locally when the human is at their machine

`keel serve` (serve a COPY of the exe if you will keep building — issue150), point them at
`http://127.0.0.1:7777/deck`. Every tap saves through tested endpoints; nothing else is needed.

### 2. Publish the mobile deck

```
keel deck . --out <scratchpad>/deck.html
```

Publish with the Artifact tool, **same file path every time** (stable URL), and declare the inbox:

```
capabilities: {mcp: {servers: [{server: "claude_ai_Smartsheet", tools: ["add_rows"]}]}}
```

- The inbox config is `.engine/contracts/deck-inbox.toml` (sheet id + column ids). `keel deck` embeds
  it; an absent or PARTIAL file makes the page claim no transport rather than half of one
  (`inbox_config_all_or_nothing`).
- **Never publish a page that calls a connector tool without having observed one real
  request/response pair for that tool in the session** (capability contract). The observed shape for
  `add_rows` is: request `{sheet_id, rows: [{toBottom: true, cells: [{columnId, value}]}]}` →
  response payload `{message: "SUCCESS", resultCode: 0, result: [{id, rowNumber, ...}]}` — the page
  treats `result[0].id` as the receipt. If the tool's shape changes upstream, re-observe before
  republishing.
- The viewer's FIRST tap prompts a one-time connector consent in the artifact frame — tell them to
  expect it.

### 3. Pull the inbox and record — the receive side

Only the session holds connector access, so the session pulls:

1. `get_sheet_summary` on the inbox sheet with filter `Processed = false`.
2. Write the rows to `rows.json` as
   `[{rowId, uid, name, kind, verdict, note, by, at, head}]` (`head` = the DeckHead column).
3. `python .engine/tools/deck_inbox_record.py rows.json --base http://127.0.0.1:7777 --root .`
   — records each row through the write API and **verifies each from the computed view**; a row is
   `verified`, `REFUSED`, `UNVERIFIED`, or `triage` (a needs-work note; nothing recorded). Dedup is
   latest-At per (uid, kind), so duplicate deliveries — the page invites a re-tap on an ambiguous
   outcome — are harmless.
4. Mark ONLY the `verified` rows `Processed = true` (`update_rows`). `triage` rows are the AI's
   work queue; act on them, then mark them.
5. When the recorder or the deck changed since the last pull, rehearse first:
   `python .engine/tools/deck_inbox_record.py rows.json --copy-test <repo>` — same loop against a
   served COPY, real tree untouched.

### 4. Provenance rules for what comes back

- A row's `By` is who the page embedded at generation time (the sole registered Person). An
  acceptance or sitting row records THEIR tap as THEIR word — the server refuses a non-Person where
  the fact is human-gated, and the recorder passes `by` through, never substitutes.
- **Never record a `method=confirmation` result from a tap that did not arrive.** No row, no fact.
- Their note is the attestation text, quoted verbatim; a verdict with no note records the verdict
  and nothing more.

## Hard-won page rules (each cost a broken publish)

- **Pass zero: the emitted script must PARSE.** `node --check` gates the build
  (`the_emitted_script_parses`); a file full of the right strings in the right places parses as
  nothing, so string audits are meaningless without it. Corollary: never append an end-of-line `//`
  comment via a line-scoped regex; write newlines in emitted JS as `String.fromCharCode(10)` where an
  authoring layer might eat a backslash.
- **The page reports its own script survival.** The LAST statement sets `data-local-js=ok`; CSS shows
  `script ok` / `script did NOT finish`, so absence is the signal (`the_liveness_marker_is_last`).
- **Branch connector errors per code, never one banner** (`needs_reauth` → reconnect;
  `server_not_connected` → add; `selection_required` → choose; `tool_error` → the reported message;
  `server_unavailable`/`upstream_error` on a WRITE → outcome UNKNOWN, invite a fresh-gesture re-tap,
  never auto-retry).
- **Verify from the EMITTED HTML, and from the SERVED page for anything the human is told to look
  at.** Version stamps are rendered text, ASCII-only.
- **Publish, then ask — never report the mobile page as working on the strength of having written
  it.** The local transport is machine-verified; the in-page connector call is the one leg only the
  viewer can exercise.

## Guardrails

- **Never author state into the deck.** It renders computed views; if a class needs a number the
  engine does not compute, add the view.
- **Key state by UUID, never by label** — the deck regenerates against a moving model.
- **Report what the deck cannot do.** The inbox transport delivers to the store, not to keel; keel
  has the verdict only after the pull. Say so when handing over the URL.

## Removal path

Delete `keel-cli/src/deck.rs`, the `/deck` and `/api/deck/sitting` routes, the two tools
(`test_deck_e2e.py`, `deck_inbox_record.py`), `.engine/contracts/deck-inbox.toml`, this skill and its
registry entry; the inbox sheet is the human's to keep or delete. Obligations remain computed by
`keel orient` and visible in `keel serve`.
